# Detection Baseline

This document defines the first defense model for the closed-loop system.

The baseline detector should be simple enough to train quickly, but strong enough to establish a meaningful benchmark.

## Primary goal

Detect synthetic fraud generated by the attack simulator while keeping false positives on legitimate payments low.

## Baseline modeling approach

The first version should use a tabular supervised model.

Recommended candidates:

- Gradient-boosted trees
- Random forest
- Logistic regression as a minimal baseline

If the dataset grows or sequence behavior becomes central, a second-stage model can be added later.

## Prediction target

The detector should predict:

- `fraud_label`: binary fraud versus benign
- `fraud_bucket`: optional multi-class bucket prediction
- `fraud_subtype`: optional finer-grained subtype prediction
- `risk_score`: continuous fraud likelihood

For the first implementation, `fraud_label` and `risk_score` are the most important.

## Input feature families

### Transaction features

- amount
- transaction type
- status
- authorization result
- channel
- rail
- merchant category

### Customer behavior features

- account age
- spend velocity
- historical decline rate
- country drift
- repeat transaction cadence

### Merchant features

- merchant age
- refund rate
- chargeback rate
- volume growth rate
- risk tier

### Device and session features

- device reuse
- IP reputation
- session duration
- failed login count
- device-country mismatch

### Sequence and graph features

- event counts in recent windows
- time since last action
- transition patterns
- linkage between customers, merchants, devices, and IPs

## Feature engineering principles

- Use the same feature pipeline for training and inference.
- Prefer interpretable features before adding complex ones.
- Keep window sizes explicit and documented.
- Avoid leaking labels or attack metadata into model inputs.

### Implemented point-in-time behavioral features

The feature builder now processes transactions in event-time order and computes features from **prior events only**. It no longer uses a full-file entity count, which would reveal future activity during training and evaluation.

Current online-style features include:

- prior transaction counts for customer, merchant, device, session, and IP;
- customer and device velocity in the preceding hour;
- customer declines in the preceding 24 hours;
- customer amount baseline and deviation from that baseline;
- minutes since the previous customer and device event.

For the prototype these states are rebuilt deterministically from the batch. In production, the same definitions should be backed by a real-time feature store or stream processor, with point-in-time correct state reads.

## Training strategy

The first detector should train on:

- benign records
- fraudulent records generated from the attack catalog

Recommended strategy:

- split by scenario or attack instance, not only by row
- hold out some attack patterns entirely for generalization testing
- use class balancing or weighted loss if needed

### Implemented generalization benchmark

The current baseline uses an **attack-card holdout** split rather than its former random row split. It withholds approximately 25% of distinct fraudulent `attack_id` values from training and combines them with an independently sampled benign holdout. All events for a withheld attack card remain out of training, so a campaign cannot appear in both partitions.

`train_metrics.json` records the held-out card IDs and transaction IDs. `evaluation_report.json` contains `heldout_attack_benchmark` with hybrid and ML-only metrics. This is the primary evidence for generalization to unseen catalog attacks; all-data scores remain useful for operational debugging but are not the novelty claim.

## Evaluation metrics

The detector should report:

- precision
- recall
- F1
- ROC-AUC
- PR-AUC
- false positive rate

If thresholds are used operationally, also report:

- recall at fixed false positive rate
- precision at fixed recall

## Explainability

The detector should expose human-readable reasons for each flag.

Good options:

- feature importance
- local explanation scores
- rule-derived reason codes

## Selective GenAI Defensive Review

The baseline model scores every synthetic transaction. A bounded second stage selects the rows closest to the ML threshold (five by default) and asks the configured GenAI provider for a structured defensive review. The LLM receives behavioral features, ML score, threshold, and explanation signals, but never the synthetic ground-truth label, attack bucket, or attack subtype.

The review returns semantic risk, novelty, recommendation, rationale, and risk indicators. A hybrid policy combines the ML and semantic risk scores. Scores output both the ML-only fields and hybrid fields so evaluation can compare the two approaches. In a live environment this reviewer belongs on ambiguous, high-impact, or novel alerts—not in the synchronous path for every payment.

Example reason codes:

- unusual device change
- abnormal transaction velocity
- beneficiary novelty
- merchant risk spike

## Thresholding

The model should support at least two thresholds:

- a review threshold for manual inspection
- a hard-block threshold for obvious fraud

This helps the prototype demonstrate operational realism.

## Why this baseline is a good first step

- Easy to train on synthetic data.
- Easy to explain to judges.
- Easy to compare against future improvements.
- Strong enough to support an end-to-end demo.
